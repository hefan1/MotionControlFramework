# ROC-19：连接同步的来源与收尾边界

## 目标与已有事实

继续 ROC-18 的来源隔离工作，使 Host 在连接通知重复、任务收尾等待、连接失效或关窗交叠时，不把旧 Runtime、页面或报警日志发布到后来连接。实现保持直白 C# 和中文注释，不调整页面布局、厂商 API 或设备停止许可。

基线为 master `be17f5c063604b06a9019dbced09a71b7ce2dea6`，其 Windows 全套检查已通过。当前实现入口是 `App.SynchronizeCardConnectionAsync` 与 `TaskMonitorLauncher.SetMachineContextAsync`，不是另建会话管理框架。

正常首次连接通常同步完成：Host 先连卡，Runtime 的 MotionCardGroup 会跳过已连接卡；没有任务时上下文设置也不等待。不能仅凭存在 await 宣称正常连接发生死锁或重入故障。需要复现的是已有任务/在途装载或监控收尾等待时的交错。

源码缺口包括：App 的 await 后没有完整来源核对；断连与失败路径继续清空共享字段；任务上下文 setter 增加代次但未在关闭等待后核对；重复同一有效连接通知可能重建 Runtime。心跳失联只锁存连接丢失，不调用同步，因此仅检查同步代次不足。

## 方案与选择

采用原具体类中的来源快照与代次核对。每轮捕获连接服务、卡、逻辑 IO、原 Runtime 及组合对象；等待后核对当前连接状态和对象身份。构造中的 safety、alarm、history、Runtime 尽量保持局部，确认当前来源后统一发布；旧清理只操作本轮对象。重复已发布连接保持幂等，避免第二个监控和运行时。

未选单纯串行门：它不能单独阻止已失效请求发布，还可能把断连通知排在旧等待后。未选通用生命周期引擎：当前只需要维护 App 与一个任务入口的明确职责，不增加间接层。以上是总协调依据既定隔离要求作出的实现选择，不改变操作员工作流。

任务入口在关闭等待后重新验证本轮上下文代次。关窗在异步断卡与同步后核对原连接以及最终已断开状态；正常清理将 Runtime 清空不算错误，后来连接则不能被旧关闭请求处理。

## 回归与证据边界

使用现有 OperatorPages.Checks、BoundTaskLoadChecks、LoadCard 和可控任务屏障，实际调用被修改的 App/任务入口。先在未修改生产代码的基线上运行，确认失败源于来源覆盖而非缺少配置或测试异常。覆盖重复通知、旧连接/断连/失败迟到、任务 setter 被连接丢失撤销，以及关窗交叠。

不新增 FakeAxis，不用内存设施声称运动 API 已验证；既有 Virtual 适配器 API 回归继续执行。中文记录区分可控离线场景与正式界面观察。当前桌面目标为 Linux，ROC-13 的正式 Windows Host 14 项仍未执行。

## 完成条件

针对性红态证据、最小修复、完整 Windows 回归、独立差异复核、中文提交/PR 与实际 master 验证齐备后更新 ROC-19。旧报警、资源隔离和恢复证据必须保留；正式窗口项目继续在 ROC-13 执行。
